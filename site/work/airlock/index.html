Airlock: reversible, privacy-preserving inference

A privacy layer for generative AI. It removes personal information before a prompt reaches an external model, then restores it in the answer for the person entitled to see it.

01Problem

People get real value from pasting work into a large language model: summarising a complaint, drafting a reply, reading a case note. That work is often full of personal information such as names, phone numbers, email addresses and government identifiers.

Organisations usually answer with one of two blunt tools: block the AI tool, or trust the provider's terms. Blocking pushes people towards unmanaged tools. Trusting the terms still sends the data out. I wanted to explore a third option: let the model do the reasoning without ever seeing the sensitive values.

02Approach

Airlock treats the model call like a clean room. Sensitive values are swapped for typed placeholders before the prompt leaves, the mapping stays inside the trusted boundary, and the real values are put back only after the answer returns.

Illustrative example of the intended behaviour, with synthetic data (not a recorded run)
StageText
Original requestSummarise: Alex Morgan called from 0400 000 000 about a refund. Reply to alex.morgan@example.com.
What the model seesSummarise: [PERSON_001] called from [PHONE_NUMBER_002] about a refund. Reply to [EMAIL_ADDRESS_003].
What the model returns[PERSON_001] wants a refund. Respond by email to [EMAIL_ADDRESS_003].
What the person receivesAlex Morgan wants a refund. Respond by email to alex.morgan@example.com.

Typed placeholders matter. A string of asterisks destroys meaning, while [PERSON_001] tells the model there is a person here, so the answer stays useful.

03Architecture

The stages below describe the prototype's design intent.

Trusted boundary

1. DetectEntity recognition finds personal information in the request.
2. TokeniseEach value is replaced with a typed, numbered placeholder.
3. Hold the mapThe placeholder-to-value mapping is kept per request in a managed secret store.
↓ sanitised text only ↑ sanitised answer

Outside the boundary

4. External modelReasons over placeholders and is instructed to keep them intact. Never receives the mapping.
↓

Trusted boundary

5. ValidateDesign intent: the answer is checked against the placeholders that were issued before anything is restored.
6. RehydratePlaceholders are replaced with the real values for the caller.
7. DiscardDesign intent: the mapping is single-request data and is not reused.

04Key decisions

DecisionWhy
Reversible, not one-way, redactionOne-way redaction protects the data but leaves the person with an answer they cannot use. Restoring values inside the boundary keeps the productivity benefit.
The mapping never crosses the boundaryDesign intent: the model only ever sees placeholders. The mapping is the most sensitive object in the system, so it is held in a managed secret store rather than sent anywhere.
Keyless application codeThe application reaches the model and the secret store through managed identity, so no keys or client secrets sit in the application code.
Refuse to restore on doubtDesign intent: if the answer contains a placeholder that was never issued, nothing is restored and the request fails, rather than guessing.
Infrastructure as code as an adoption baseline firstThe first template describes the existing cloud resources without creating or changing any. A documented preview (what-if) step comes before any template is allowed to make changes.

05Security and governance

Airlock applies a familiar data loss prevention idea (sensitive data should not leave) at a new boundary: the prompt. It complements platform controls such as sensitivity labels and DLP policies, and does not replace them.

The honest framing matters most here. Detection is probabilistic, so a layer like this reduces exposure. It does not guarantee that nothing sensitive leaves. Anyone deploying it needs measured detection coverage for the identifiers that matter in their context, such as Australian phone numbers, addresses and government identifiers, before any real data goes near it.

06Evidence and result

2 daysFrom empty repository to a working end-to-end flow
SyntheticData only: the prototype has been run with synthetic data only
0 claimsAbout accuracy, until an evaluation set exists

What exists: a reversible core, an end-to-end flow against a model hosted in Azure AI Foundry, a serverless API in front of it, and an infrastructure baseline. It has been run with synthetic personal data only.

What does not exist yet: an evaluation set or any accuracy, coverage or latency figures. That is why this case study is labelled prototype and not yet evaluated, and why it contains no performance claims.

07What I learned

  • Reversibility moves the risk rather than removing it. Once values can be restored, the mapping becomes the crown jewel. Its lifecycle deserves more design attention than the model call.
  • Evaluation comes before claims. The next step is a labelled test set of realistic Australian identifiers, measured before any statement about accuracy is made.
  • This is a platform conversation as much as an engineering one. In an enterprise, the same outcome may be better served by platform controls such as sensitivity labels, DLP for AI and approved-model routing. A custom layer earns its place only where those controls cannot reach.
