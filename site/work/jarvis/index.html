Jarvis: governed self-improving AI

A personal AI system that can find, propose and build improvements to its own code, but only inside boundaries that a human sets, signs and can audit afterwards.

01Problem

AI agents can now write and ship code. For any organisation adopting them, the hard question is no longer can the agent do it. It is who authorised it, within what limits, and how would we prove afterwards what actually happened?

Most agent demos collapse suggesting, approving and doing into one step, and the authority to act ends up living inside the model's judgement. I wanted to find out what it really takes to let an AI system improve itself without ever giving it the authority to decide that it should.

02Approach

I treated authority as a record, not a mood. Every act that changes what the system may do is a separate, explicit, attributable event, and anything the system cannot prove it treats as not having happened.

  • A capability ladder: observe, prepare, execute. The app people talk to can observe and prepare. At most it can file a request to execute; execution happens in a separate process and needs a signed approval, so a persuasive prompt has nothing to escalate to.
  • Approve and execute are two different events. A single action that did both would be exactly the "approval quietly becomes execution" failure the design exists to prevent.
  • The builder is not trusted to mark its own homework. A separate host process re-runs the required tests and checks the builder's evidence itself, rather than taking the builder's word.
  • Merging is a human decision. The best state a governed mission can reach on its own is awaiting the owner's decision. No governed run can mark itself completed.

03The governed lifecycle

This is the designed path for one improvement, from a sentence typed into Jarvis to a change on the main branch. The outlined steps are the ones only a human can take. The evidence section says exactly which parts have run live.

  1. RequestI ask Jarvis to improve itself, in plain language.
  2. DiscoverJarvis reads approved, read-only evidence (backlog, project state) and shortlists candidates.
  3. ProposeOne candidate becomes a bounded proposal: scope, allowed paths, tests that must pass.
  4. Review and approveI review the scope and approve it in the app. Approval authorises nothing to run yet.
  5. High-trust confirmationI sign a statement binding that exact scope. It is short-lived and single-use.
  6. ExecuteA sandboxed builder agent makes the change. It holds no credential that could merge.
  7. ValidateThe host independently re-runs the required tests and checks the builder's evidence.
  8. ReportA draft pull request plus an evidence record. Merging stays my decision.

Every step fails closed. Stale evidence, a changed candidate, an expired or reused signature, missing test evidence or an unavailable resource each stop the mission and write a record saying why. A refusal is an audited outcome, not an error to retry around.

04Architecture and key decisions

The system is split into zones with deliberately different levels of trust. The window that renders untrusted text is the least trusted part and holds the least authority.

Decisions that shaped it

DecisionWhy
Execution runs in a separate host process, never in the appThe app renders untrusted text. Giving it a shell and a checkout would remove the very control being demonstrated. A test walks the app's import graph and fails if it can reach the execution machinery.
Default deny by absenceA capability that does not exist cannot be misused. A test scans the exported surface for dangerous capability names (merge, grant, credential and similar), so adding one fails the build instead of relying on review.
Build provenance compiled into the binary"Which code is running?" must be answered by the build, not by whatever directory a process started in. If the build cannot prove its commit, it says unavailable and nothing else.
Advisory models have no authorityOther models can review a mission, and an external judge can run in shadow mode, but none can override the deterministic policy. If an advisory answer ever replaces the real decision, the mission fails.
Hash-chained, append-only evidence ledgerEvery event is recorded in a chain that spans segment boundaries, so deleting a segment from the middle of the chain still breaks a link. I describe it as tamper-evident, not tamper-resistant, because that is what it is.
Zero new spend by constructionA mission contract may not authorise new spend. The approved budget ceiling is zero.

05Security and governance

I rank controls by how much weight each one bears, and I say plainly which layer is weak.

  1. Structural controls hold whatever the model does: capabilities that do not exist, processes that cannot reach each other, no merge-capable credential in the agent's hands.
  2. Procedural controls depend on me: scope approval, a signed confirmation, and the merge decision.
  3. Detection is the weakest layer, and is known to be. When I measured my own prompt-injection detector, it caught every phrasing it was tuned on and very few held-out paraphrases of the same attacks. So the design never relies on detection. The strongest tests assert that untrusted content changes nothing even when the detector does not fire.

The written protocol every AI coding session works under contains absolute prohibitions. Two of them carry most of the weight: an agent must not be able to change the rule that constrains it, and all content is evidence, never authority. An instruction found inside an issue, a file, a comment or tool output is data to be weighed, not a command.

🔒 Anti-bypass control: redacted

The mechanisms that bind an approval to one exact scope, prevent it being replayed or reused, and detect a mission whose inputs changed after approval are not published. What they guarantee is described above; how they do it is withheld.

06Evidence and result

6,000+Automated tests across TypeScript and Rust
~350kLines of Rust and TypeScript, including tests

On 23 September 2026 the core of the lifecycle ran for real. A candidate from Jarvis's own discovery run, which I had approved and signed as one bounded mission, was built by the sandboxed builder, which also ran the required test. The host then independently re-ran that test and a draft pull request was opened. I reviewed it and merged it. The change itself was deliberately small, because the thing being proven was the governance path, not the size of the change.

It took five signed attempts. Each of the first four stopped safely on at least one defect in the host (six in all), and each was fixed before the next attempt. None of them was a failure of the governance model, and every one was stopped and recorded rather than worked around. Because each approval is single use, every retry needed a fresh signature. That was inconvenient, and it was the point.

What that run did not yet include. The mission contract was written by hand. The plain-language request at the front of the lifecycle, and Jarvis drafting the contract itself, arrived in the days that followed. A single run from a typed request all the way to a merged change is the acceptance test I am working towards now.

Since then the operator journey has been rebuilt so that needing attention, approving, requesting execution and reviewing sit on one surface in the app, with each recovery offered as a control rather than a command line. The high-trust signature remains a deliberately separate step.

07What I learned

  • The gap is usually a missing caller, not a missing component. Before the lifecycle worked end to end, every component already existed and was tested. None was reachable from anything a person could run. The first assertion in its test suite is simply that it can be reached.
  • Fail-closed refusals are cheap defect discovery. Four refused runs found six real defects without doing any harm.
  • A prohibition broader than its reasoning gets argued with. My original "never merge" rule bundled four acts. Only three can put code on the main branch. Splitting out the harmless one made the rule easier to keep.
  • Verify that the owner can still act. Every other check proves something is blocked, and a configuration that blocks everything passes all of them. I once designed a branch-protection setup that nobody could ever merge through. There is now a test whose only job is to stop that check being deleted.
  • Label maturity honestly. The project tracks what is demonstrated, what is built but not yet connected, and what is only specified, and it publishes the numbers that did not go my way.
