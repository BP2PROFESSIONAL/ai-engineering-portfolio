Information protection: governed AI sensitivity labelling

An on-device AI model proposes a Microsoft Purview sensitivity label for each file. Policy decides what is allowed, a person approves each write, and every label is proven by reading it back.

01Problem

Microsoft 365 Copilot and similar tools respect sensitivity labels, which makes labelling coverage one of the most important controls in any AI rollout. Yet most organisations have large volumes of unlabelled content, and nobody can label it all by hand.

AI can help classify content. Handing it the power to change labels, however, turns a classifier's mistakes into policy. It also usually means sending document content to yet another service to be read. I wanted to know whether AI could help close the coverage gap without the content leaving the machine and without the model holding any authority.

02Approach

The model proposes. Policy decides. A person approves. Graph executes. Purview enforces. The audit trail proves it.

  • Classification runs on-device. A small language model running locally reads each document. The document content never goes to an external AI service.
  • The model can never write. Its output is a proposal checked against a strict schema. Malformed output is rejected, not repaired. A deterministic layer of sensitive-content indicators sets a floor the model cannot go below without human review.
  • Every write needs a person. Approvals are made in a familiar tool (an Excel workbook). The system trusts only the approval columns and re-derives everything else on import.
  • Proof is a read-back, not an API response. A label counts as applied only when it is read back through a separate, read-only identity.

Human authority

4. ApproveA person approves each file's label in a workbook. Each approval is single use and expires.

Separate write identity

5. ApplyA write gate with one permitted path and fifteen named refusals. The file is re-read immediately before each write.

Read-only identity

6. VerifyRead the label back. Anything not yet visible is re-read later, never re-written.

04Security and governance

The write gate is a pure function with exactly one path that permits a write. Everything else is a named refusal, and every attempt, refused or not, writes an evidence record. Among the fifteen refusals:

  • No approval: a classification is never an approval.
  • Approval already used or expired: an approval authorises one write, not a standing permission.
  • File or label changed since approval: the person approved what they saw, not whatever is there now.
  • Current label unknown, or two sources disagree: a blind write is refused.
  • Downgrade not separately approved: lowering a label needs its own explicit authority.

Reading and writing use two separate app identities with the narrowest delegated permissions that do the job. Label removal cannot be expressed at all. Batches are frozen manifests identified by a digest, so any edit makes the batch stale, and a single command-line limit caps how many files a run may touch.

Model quality was measured separately on a small golden set before any write: four of five cases exact and no under-classification. 06What I learned

  • An accepted request is not an applied label. The API accepts a label write and applies it later, and its own status can lag behind the file. Only a read-back counts, and a read may be repeated where a write may not.
  • Deterministic floors catch what models miss. On a long document with sensitive material buried in it, the model labelled every chunk Internal. The rule-based indicator floor caught the sensitive section.
  • Map the model's vocabulary to the tenant's, not the other way round. Ambiguous mappings map to nothing, so they fail closed.
  • Platform behaviour is part of the design. Label replication, permission errors that look like missing files, and preview-only API routes all changed the architecture. Each one is now a documented first check rather than a surprise.
  • Local models are ready for proposals, not verdicts. The on-device model was good enough to shortlist labels. It was not good enough to be trusted alone, and the design never asks it to be.
