Disclosure policy

What I publish, what I withhold, and how I decided

A portfolio about governed AI should be governed too. This page explains the rules this site was built under, so that what is missing reads as a decision rather than a gap.

The publication model

  1. The working repositories stay private. None of the source repositories behind this work has been made public. Their visibility has not been changed.
  2. Allow-list, never copy-then-redact. Every page here was written from scratch from material deliberately selected for publication. Nothing was copied in wholesale and then trimmed, so there is no earlier, fuller version hiding in this site's history.
  3. Redaction happens before publication. Sensitive detail never entered this site's repository at any point: not in commits, branches, comments, page source, metadata or build output.
  4. Fail closed. Where I was unsure whether something was safe to publish, I left it out.
  5. Every claim carries its status. Each result is labelled demonstrated, measured, prototype, proposal or hypothesis, with its limits stated. No metric was invented or rounded up.

What is published

  • The problem, the approach, the design intent and the security outcome of each piece of work.
  • Architecture at the level of zones, responsibilities and decisions.
  • Measured results with their method, sample size and limits, including the ones that went against me.
  • Illustrative examples built from synthetic data. Screenshots of the working systems are not published.

What is withheld, and why

CategoryWhy it is withheld
Secrets, keys, tokens and credential architectureObvious for the values. The architecture is withheld too, because knowing where credentials live and who may read them is most of an attack plan.
Trust-boundary implementationHow components exchange requests and how sandboxes are constrained is exactly what an attacker would need to cross them.
Anti-bypass and anti-replay mechanismsWhat they guarantee is published. How they work is not.
Host and infrastructure identifiersMachine names, file locations, tenant, subscription, app, certificate and label identifiers, endpoints and signing identities serve no reader and help an attacker.
Private security tests and open findingsAttack corpora, red-team case lists and unresolved findings stay private.
Employer and third-party intellectual propertyEverything on this site is personal work. Employer work, data, configuration and internal metrics are not included.
Personal dataIncluding my own. Some experiments used my personal files and media as test data. Their names and contents are never shown.

The redaction markers

Where a gap would otherwise be confusing, the page shows a visible marker instead. The markers used on this site are:

🔒 Security redaction: implementation detail intentionally withheld

The default. Used whenever naming a more specific category would itself reveal something.

🔒 Trust boundary implementation: redacted

How separated components communicate or are contained.

🔒 Anti-bypass control: redacted

How a guarantee such as single-use approval is enforced.

🔒 Secret and credential handling: redacted

Where credentials live and which component may read them.

🔒 Host / infrastructure detail: redacted

Identifiers, names, locations and configuration of machines and cloud resources.

🔒 Private security test: redacted

Attack corpora and test cases.

🔒 Employer / third-party IP: not included

Work that belongs to someone else.

Two rules govern the markers. A marker must not leak by implication: if naming the category would hint at an architecture or a weakness, the generic marker is used instead. And markers are used sparingly. They are there to show judgement, not to make the pages unreadable.

How the site was checked before publication

  • A written allow-list of every file, reviewed by me before anything was made public.
  • An automated pre-publication check, included in the repository and run on every push. It looks for credential-shaped strings, private keys, identifiers, private hostnames and file paths, personal contact details and internal ticket references, and it proves on every run that each pattern can fire, so a silent scan is never mistaken for a clean one.
  • Before any publication, the same check is run locally against a private deny-list of specific names. That list cannot live in the public repository, because the names themselves are private, so the check refuses to report a pass without it unless it is told explicitly that it is running in public CI, where it says so in its output.
  • A review of the full Git history, not just the latest version, before the repository was made public.

How this site treats you

No JavaScript, no cookies, no analytics, no web fonts and no third-party requests. A strict content security policy allows the page to load only its own stylesheet.
